# Crowd Ripple

**A crowdedness-aware bus journey planner for Delhi.** Transport Stack Hackathon 2026, Problem 2.

> Journey planners rank buses by time. Delhi commuters also ask: *will I get a seat, or will the bus be too full
> to board?* Crowd Ripple learns how full every bus usually is, by route, stretch, day type and hour, from
> ~2.5 million October 2026 tickets. It shows that next to every journey option, so commuters can choose
> between a faster trip and a more comfortable one.

It also brings in the idea from our earlier project **Ripple** (cascading effects of a disruption): crowding
spreads. A full bus leaves people behind, and they crowd the next bus and the parallel routes. So:
- the planner turns crowding into **extra waiting time** ("+6 min: full buses may pass you");
- the operator console simulates **what one breakdown or a metro disruption does next**, as 1st, 2nd and
  3rd-order effects with an action for each, and ranks **where one extra bus helps most**.

## Run it

Needs Python 3.10+ and internet for the first download and the map tiles.

```bash
pip install -r requirements.txt
python -m pipeline.download        # ticket data (66 MB) + Delhi GTFS (19 MB) into data/
python -m pipeline.build           # ~1 min: builds data/processed/model.pkl and crowding.sqlite
python -m validation.validate      # checks vs known patterns -> docs/VALIDATION.md
python app.py                      # http://127.0.0.1:8000
```

## API

```
GET /journeys?from=Anand Vihar ISBT Terminal&to=Super Bazar Conn. Place&depart=2026-10-27T18:00&comfort=0.5
GET /journeys?from=28.6469,77.3159&to=28.6328,77.2195&depart=2026-10-27T18:00
```

Each option returns legs (walk / bus / transfer walk / bus / walk), boarding and alighting stops and times,
wait (including the full-bus delay), ride time, and per-stretch crowding (`seats | standing | crowded | packed`)
with estimated load. Each option also has `crowding.worst_level`, `seat_chance` and `confidence`, plus tags
(*Fastest*, *Most comfortable*, *Best for you*, *Leave 20 min later*).

| Endpoint | Returns |
|---|---|
| `GET /api/crowding/route/{route}?daytype=weekday` | load per bus and level for every stretch × hour of a route |
| `GET /api/crowding/network?daytype=&hour=` | busiest stretches citywide with typical level (map layer) |
| `GET /api/hotspots?daytype=&hour=` | route-hours where one extra bus removes the most crowded passenger-minutes |
| `GET /api/ripple?event=cancel&route=525DOWN&hour=18` | cascade of a breakdown: next bus, left-behind riders, spill-over to parallel routes, missed return trip |
| `GET /api/ripple?event=surge&lat=28.6675&lon=77.2285&riders=3000&hour=18` | a demand surge (e.g. metro line down at Kashmere Gate) |
| `GET /api/ripple?event=add&route=413UP&hour=9` | effect of adding one bus |
| `GET /api/stops?q=`, `GET /api/routes?q=`, `GET /api/meta`, `GET /api/validation` | helpers |

The crowding model can also be queried without the app: `data/processed/crowding.sqlite`, table
`segment_crowding` (route, daytype, hour, stretch, riders/hour, buses/hour, load per bus, level, tickets).

## How it works (short)

1. **Tickets → stretches.** Match each ticket to its GTFS route and place its boarding and alighting stops on
   the route (exact, partial and fuzzy name matching, then geographic snapping). 72% of riders are placed.
   A running count along the route gives riders on every stretch, for every day and hour.
2. **Sample → everyone.** These are app/QR tickets (10%-discounted fares), ~102k a weekday. A city-wide factor
   (×39, from ~40 lakh daily boardings) accounts for pink-ticket, pass and cash riders. If the implied load
   exceeds crush capacity, the bus count is raised (more buses ran than the old schedule lists). Sparse
   route-hours are shrunk toward the route's usual load.
3. **Load → level.** Seats / standing / crowded / packed by bus size (12 m vs 9 m DEVI), plus seat chance and
   full-bus probability from bus-to-bus and day-to-day spread.
4. **Planner.** Direct and one-transfer journeys on GTFS, scored on perceived minutes, where crowded minutes
   count more as the comfort slider rises.
5. **Ripple.** Breakdowns and surges are pushed through the network (following buses, parallel routes, return
   trips) to give a timeline of effects with suggested actions.

## Headline checks

- Peaks at **09:00** (5.2× midday) and **18:00** (3.5×); Saturday 79% and Sunday 49% of a weekday; Gandhi
  Jayanti and Dussehra visibly low.
- Crowded or packed: **45% of riding at 9am vs 10% at 2pm**; Sunday 9am 14%.
- **Hold-out week:** Spearman 0.70 on load per bus; same crowding level for 63% of riders, within one level
  for 91%.

## Project layout

```
config.py            every assumption in one place (capacities, levels, expansion, planner weights)
pipeline/            download.py, gtfs.py (route patterns, run times, buses/hour), build.py (tickets -> model)
crowd/               flows.py (running counts), levels.py, store.py (model queries), planner.py, ripple.py
validation/          validate.py -> data/processed/validation.json + docs/VALIDATION.md
app.py               FastAPI app and API
static/              index.html (commuter planner), operator.html (operator console), style.css
```
